# Increment 10 — Per-Priority Semantic Zoom on Pie Chart

## Goal

Enable the LLM to re-render the weekly report pie chart with a **semantic breakdown of any single category** — one at a time. The user asks "break down my P1 time" and the pie chart re-renders showing P1's subcategories alongside the other categories as single slices.

This extends the existing semantic grouping mechanism (currently only for non-priority "Other" time) to work for any slice: P1, P2, P3, or Other. **Only one category can be exploded at a time.**

---

## Context

### What exists today

- `get_weekly_report` tool accepts optional `semantic_groupings` parameter — an array of `{category, hours, event_count}` objects
- When `semantic_groupings` is provided, `_build_pie_slices` replaces the "Other" slice with the user-confirmed semantic categories
- `allEvents` in the response includes every calendar event with `matchedKeywords` per event — the LLM already has the raw data to group within any priority
- `assistant_guidance` currently only instructs the LLM to propose semantic groupings for non-priority time
- The PieChart widget component renders any mix of `priority` and `semantic` type slices — it does not care what they represent

### What the LLM told the user today

When asked to subcategorize P1 in the pie chart, the LLM responded: "The pie chart only supports individual priorities (P1, P2, P3) and semantic breakdown of non-priority time. It does not support subcategories inside a single priority."

This is correct given current `assistant_guidance`. This increment removes that limitation.

### Design constraint

The pie chart shows **one zoom level at a time**:
- Default: P1 + P2 + P3 + Other (4 slices max)
- Zoomed into P1: P1-subcategory-A + P1-subcategory-B + ... + P2 + P3 + Other
- Zoomed into Other: P1 + P2 + P3 + semantic-A + semantic-B + ...
- Never: P1 subcategories AND P2 subcategories simultaneously

### Data compliance

Semantic groupings are ephemeral — generated by LLM during conversation, never persisted. Event titles/descriptions are consumed in-memory only. No new data is stored. This is consistent with the data retention strategy (see project knowledge: "Semantic groupings — Ephemeral, generated by LLM during conversation. Non-deterministic, not reproducible, therefore not meaningful to store.").

### Architectural boundary: MCP stays deterministic

All semantic grouping logic lives in the LLM. The MCP tool receives pre-grouped data via `semantic_groupings` and renders it — it never computes, infers, or re-groups categories. MCP must not read `allEvents` to compute groupings. It may only use hour totals from `time_allocation`/`keywords` for validation. This boundary must not be violated.

---

## Architecture Decisions

| Decision | Choice | Rationale |
|---|---|---|
| New parameter vs reuse `semantic_groupings` | Add `semantic_target` parameter alongside existing `semantic_groupings` | `semantic_groupings` already carries the grouped data. `semantic_target` tells `_build_pie_slices` which category to explode. Clean separation of "what to zoom" vs "what the groups are". |
| `semantic_target` values | `"P1"`, `"P2"`, `"P3"`, or `"other"` | Maps directly to existing keyword/slice types. `"other"` preserves current behavior when combined with `semantic_groupings`. |
| Validation errors | `ToolUsageError` (not structured error returns) | Input validation failures are simple flat messages. Consistent with MCP standard: `ToolUsageError` for input validation, structured errors for domain-level rejections (e.g. `MAX_PRIORITIES_REACHED`). |
| Widget changes | None | PieChart already renders any combination of `priority` + `semantic` slices. The only change is in what data gets sent. |
| Backend changes | None | `allEvents` with `matchedKeywords` is already returned. All grouping happens LLM-side. |

**No changes.**

## Layer 2: MCP — `get_weekly_report.py`

**File:** `mcp_server/priority_guardian/tools/get_weekly_report.py`

### A. Input schema change

Add `semantic_target` to `INPUT_SCHEMA["properties"]`:

```
"semantic_target": {
    "type": "string",
    "enum": ["P1", "P2", "P3", "other"],
    "description": (
        "Which category to explode into semantic subcategories. "
        "When set, the named category is replaced by its semantic_groupings "
        "while all other categories remain as single slices. "
        "Only one category can be expanded at a time. "
        "Requires semantic_groupings to also be provided."
    ),
}
```

### B. `_build_pie_slices` logic change

Current behavior: when `semantic_groupings` is provided, **always** replaces "Other" slice with semantic categories.

New behavior: when `semantic_target` is provided alongside `semantic_groupings`:

- If `semantic_target` is `"other"` → current behavior (replace Other with semantic slices). This is the backwards-compatible default.
- If `semantic_target` is `"P1"`, `"P2"`, or `"P3"` → replace that priority's single slice with the semantic subcategory slices. All other priorities + Other remain as single slices.

Validation rules (all raise `ToolUsageError`):
- `semantic_target` provided but `semantic_groupings` is empty/missing → `ToolUsageError("semantic_target requires semantic_groupings to be provided.")`
- `semantic_target` is a keyword (P1/P2/P3) but that keyword is not configured as an active priority → `ToolUsageError("No active priority found for {semantic_target}.")`
- `semantic_target` is a keyword and grouped hours total exceeds that keyword's actual hours by more than 0.5h → `ToolUsageError` with message (same tolerance pattern as current Other validation)
- If `semantic_target` is not provided but `semantic_groupings` is → default `semantic_target` to `"other"` (backwards compatibility)

Remainder rule (applies to all targets — priorities and "other" alike):
- If grouped hours total is less than the target category's actual hours and the remainder is ≥ 0.25h → create an "Uncategorized" slice (`type="semantic"`) with the remainder hours. This matches the existing behavior for "Other" zoom. If remainder < 0.25h, absorb it (rounding noise).

### C. `_build_assistant_guidance` changes

Update the guidance text for both modes:

**MODE 1 (no semantic_groupings):** Add to the existing guidance after the current semantic grouping proposal paragraph:

"You can also propose a within-priority breakdown for any single priority. If the user asks to see where their P1/P2/P3 time went, analyze the keyword-matched events for that priority from allEvents, propose approximate semantic categories based on event titles and descriptions, and if confirmed, call get_weekly_report again with semantic_target set to the keyword and semantic_groupings containing the confirmed within-priority categories. Only one category (a priority or 'other') can be expanded at a time."

**MODE 2 (semantic_groupings provided):** Replace existing text with:

"The pie chart now shows the refined breakdown for the selected category. Do NOT repeat or list the categories — the chart displays them. Make a brief neutral observation about the allocation pattern without evaluation or recommendation. Ask what stands out to them. Keep it short — the visual does the heavy lifting."

**Important:** The existing MODE 2 text says "coaching observation" — this violates the PG product contract (mirror, not advisor). The replacement above uses "neutral observation without evaluation or recommendation." This wording fix applies regardless of this increment's new functionality.

### D. Handler logic

Extract `semantic_target` from arguments. Pass it through to `_build_pie_slices`. Default to `"other"` when `semantic_groupings` is provided but `semantic_target` is not.

### E. Logging

The existing `tool.get_weekly_report.start` structured log must include `semantic_target` value alongside the existing `has_semantic_groupings` and `grouping_count` fields.

## Layer 3: Widget

**No changes.**

PieChart.tsx already renders slices generically based on `type` ("priority" or "semantic") and assigns colors accordingly. When the MCP returns P1 subcategories as `semantic` type slices alongside P2/P3 as `priority` type slices, it renders correctly.

Verify: the `SEMANTIC_COLORS` array in PieChart.tsx has 8 colors, which is sufficient for typical within-priority breakdowns (3-6 subcategories).

## Unit Tests

**File:** `tests/unit/mcp_server/priority_guardian/tools/test_get_weekly_report.py` (or appropriate existing test location)

Tests for `_build_pie_slices`:

1. **Backwards compatibility — semantic_groupings without semantic_target:** Behaves identically to current behavior (Other is replaced). Validates no regression.
2. **semantic_target="other" + semantic_groupings:** Same as backwards-compatible behavior — Other slice replaced by semantic subcategories.
3. **semantic_target="P1" + semantic_groupings:** P1's single slice is replaced by semantic subcategory slices. P2, P3, Other remain as single slices.
4. **semantic_target="P2" + semantic_groupings:** Same pattern for P2.
5. **semantic_target with empty semantic_groupings:** Raises `ToolUsageError`.
6. **semantic_target with no semantic_groupings:** Raises `ToolUsageError`.
7. **semantic_target references unconfigured priority (e.g. P3 when only P1, P2 exist):** Raises `ToolUsageError`.
8. **Grouped hours exceed target priority's hours by > 0.5h:** Raises `ToolUsageError`.
9. **Grouped hours within 0.5h tolerance:** Succeeds, remainder handled correctly.
10. **semantic_target references keyword with 0 hours this week:** Succeeds with only semantic subcategory slices for that keyword (may all be 0h), other slices unaffected.

Tests for `_build_assistant_guidance`:

11. **MODE 1 guidance includes within-priority breakdown instruction:** Verify the guidance text mentions analyzing keyword-matched events and the `semantic_target` parameter.
12. **MODE 2 guidance uses neutral wording:** Verify guidance says "neutral observation" and does NOT contain "coaching" or "recommendation".
13. **MODE 2 guidance is generic (not hardcoded to "Other"):** Verify guidance works for both priority-zoom and other-zoom scenarios.

Tests for handler:

14. **Logging includes semantic_target:** Verify `tool.get_weekly_report.start` log entry contains `semantic_target` field.
